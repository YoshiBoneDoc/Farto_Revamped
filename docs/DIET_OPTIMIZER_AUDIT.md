# Diet optimizer audit — Phases 1 and 2

Audited October 16, 2026. **Documentation and read-only investigation only. Consolidation is not approved and has not begun.**

This report follows [the consolidation instructions](../resources/DIET_OPTIMIZER_CONSOLIDATION.md). Source locations refer to the working tree audited today, not the older handoff. `D` below means `scripts/TeresMimicDiet.ash`, `L` means `scripts/TeresMimicDietLive.ash`, and `B` means `scripts/teresBARF.ash`. Each function in D has an exact declaration/caller inventory in Appendix 1.

## Findings that determine the consolidation scope

1. Keep the practical planner as the production search. Neither legacy implementation has demonstrated a better complete two-day diet under the current model.
2. The original optimizer has genuinely useful ideas: quantity-based grouped knapsack, marginal refill valuation, organ-clearing meals, deliberate allocation of noodle duration charges, and early Salty Mouth comparisons. Preserve those ideas here; adapt and benchmark selected ones separately after cleanup.
3. The experimental beam has more flexible action ordering, wish choices, and pour/expiry boundaries. Its state selection and completion behavior are unreliable. Widening it previously increased runtime without producing a legal completed diet.
4. Most of the large two-day state model is **shared production machinery**, even where it was introduced for the beam. Removing everything between the old and quick planners would break planning, candidates, replay, and live execution.
5. Two deletion traps are confirmed: `barfOde()` and `barfSynthesisCandies()` are defined among the oldest functions but still have active production callers. The benchmark also locates functions by literal source strings, including an unused cold-offer reader.
6. A current complete practical core schedule is expressible using the beam's legal action repertoire within its step limit. This audit traced one offline schedule in 123 action applications, including fixed milk and finishing. That bypasses pruning and does not rehabilitate the full beam.
7. `joint buff pairs 0` can be caused by reaching that search after the budget has expired. The counter measures eligible pairs generated, not completed pair comparisons. Current code and an isolated deadline probe substantiate this explanation; the exact historical screenshot lacks enough accompanying state/log context to establish its cause conclusively.

### A3. Family comparison

| Dimension | Original organ optimizer | Experimental full-day beam | Active practical planner |
| --- | --- | --- | --- |
| Objective | Flat configured/current adventure value, immediate effect-rate coverage, purchase/opportunity estimate; no distinct tomorrow block | Shared two-day partial `Score`; completed result uses shared `FinishState` | Completed farming income minus opportunity costs plus distinct retained-effect tomorrow value; intermediate fill scores remain approximate |
| Search unit | Item quantities grouped by effect, organ-by-organ bounded knapsack | Individual consumption/resource/gear/farm actions across the day | Complete staged schedules, with bounded partial-state DP per organ fill |
| Candidate breadth | Hardcoded lists plus `teresBarfFoods/Drinks/SpleenItems`; level/specific-item guards and special live routines; no general unrestricted-item check | Shared dynamic candidate pool; offers supported mixed/special entries as individual actions, subject to current quality filters | Same shared pool, with a smaller legal fill menu and explicit special-handler exclusions |
| State selection | One best value per group/space/helper-charge cell | One global width-limited frontier per layer, heuristic score and coarse-key merging | Default one fill state per filled amount; selected wider trial normally two, capped four; exact deduplication and conservative dominance; failed one-wide fill retries two-wide |
| Completion | DP initializes all capacities to zero, so it permits leaving space unused; no two-day proof | Tries `FinishState` for each retained parent; no full target/replay requirement inside `Search` | Complete fallback required; `MeetsTargets`; selected/reported comparisons replayed by production entry |
| Limits | Fixed loop caps: 100 fill iterations, 12 organ trades; no comparable complete-day time budget | `teresBarfDietSearchSteps`, default 160; no native wall-clock cutoff in `Search`; harness separately injects a deadline | Fallback before expiration; default `teresBarfDietPlanSeconds=90`, up to two improvement passes; pricing/setup/replay outside timer; fallback may exceed deadline |
| Accurate shared forecasts | No complete staged economic model | Uses current shared simulator, not an independent more accurate economy | Uses the same simulator for complete schedules and live replanning |
| Live behavior | Buys/consumes during optimization helpers | Simulates only | Preview simulates; explicit `run` executes via separate driver |

The beam's `earlyFill=true` mode permits farming/capacity transitions only after current ordinary organs are full and omits the explicit retained-consumption branch. This is a separate immediate-fill comparison policy; the current offline caller passes false and no production CLI exposes either mode. It is not the practical planner's complete fallback.

Original grouped-knapsack complexity is approximately `O(G × R × (H+1) × N × Q × (H+1))` for its literal nested loops: effect groups G, organ room R, helper-charge budget H, candidates N, quantities Q. It scans all candidates inside each group. It avoids order permutations but is not an unconstrained global optimizer. Beam work is approximately layers × width × action variants × transition/score cost; expensive farm variants amplify this substantially. Practical work is complete-trial count × staged fills/simulation; a fill expands roughly room × retained partial width × menu size, with cloning/scoring and sometimes dominance comparisons per expansion. These are structural bounds, not newly measured runtime claims.

Two accuracy boundaries matter before reusing old techniques:

- Original `barfPrice` values an untradeable item at zero only when physically in inventory; otherwise it returns -1. Legacy candidate eligibility can count closet/storage/stash supply that this price path then rejects. It does not provide the revised recipe opportunity-cost model. Original cooling waits for 625 XP to leave a 400-XP buffer but never implements the mandatory doubled cold-fashioned; it is not policy-equivalent to the revised planner.
- `barfDietCanCraft` whitelists Meatpasting/basic Cooking types; that whitelist alone does not prove a particular account can craft the item for zero turns. The actual executor checks `creatable_turns(...,true)` before creation, whereas candidate construction does not make that same check. Free-crafting access in other account states **needs verification**. The audit diagnostic explicitly labels its added cooking-access fixture. Do not change this modeling/execution boundary as part of deletion cleanup.

Expected income includes item opportunity value; liquid income excludes unsold drops for purchase feasibility. The simulator does not finance shopping by assuming item drops were sold. Whole-day absolute profit remains a model, especially on the incomplete saved snapshot.

### B1. What the beam failure does and does not establish

The [historical width comparison](../resources/diet-snapshot/beam-profile.md#L390) tested widths 8/16/32/64 with 171 candidates and 160 layers. Reported runtimes were 49.058/95.160/190.371/379.252 seconds. None returned a complete legal diet. Across all final retained states: 127 farm rows, mask 12, no Stooper, used liver 23, required cold-fashioned pending. These runs used the older 500k cold-fashioned price and other older assumptions; their profits/runtimes are not current live benchmarks.

Confirmed code risks consistent with that failure:

- `Search` does not reserve four liver for mandatory cold-fashioned or future cooling drinks before ordinary consumption; practical `QuickFillStage` does. At full mask-12 liver with an outstanding four-liver drink, the remaining daily clearers/slots may not suffice.
- Each selected farm action consumes a layer. Repeated 1/5-turn choices can occupy the action budget while consuming valuable effects and failing to advance capacity stages.
- Partial `Score` assumes normal farming for the remaining adventure pool, approximates expiry, and has no general completion/mandatory-resource guarantee or explicit full future-training opportunity charge. It is not completed profit.
- `Offer` uses the coarse `StateKey` after its exact duplicate check. The coarse key floors minimum adventures, omits exact expected adventures/financial totals, and folds elapsed turns modulo 31. A higher heuristic score is not proof that the other state has inferior future feasibility or liquidity. No particular collision has been proven to cause the historical failure.
- `Search` has no diversity/feasibility quotas or target validation equivalent to the active `MeetsTargets`. Capacity's shared training guard does force some charging before the first swap, but that is not a substitute for every terminal target.

Actual repertoire limitations in today's beam:

- No `barfDietExtraState` offers for chocolates/tofu/clocks.
- No timed-pour policy/skip or explicit cooling-reservation-release actions. Generic repeated pours exist. A release can sometimes be an economic no-op if every reserved refresh was used.
- Nonzero Yeti modes are offered prepared only; bare variants are offered for normal/retained mode zero. A practical bare Yeti choice need not be an exactly offered transition when helper preparations differ.
- Beam checks `!LowQuality` where practical also permits its explicit delayed-adventure quality exception. For a low-quality delayed item, its presence in the shared pool does not ensure ordinary beam reachability.

These newer repertoire gaps do not, by themselves, explain the older experiment which preceded some newer features.

**Read-only completion trace performed in this audit:** using the current source and October 13 reconstruction, enable the harness's explicitly labeled cooking-access fixture, initial seven cooling slots/full-coverage policy, and disable optional extras. Build a complete practical schedule, then independently walk its consume/resource/capacity/Stooper/pour/finish actions. For farming, decompose each row into legal targets from the beam's actual target set, including its sweat and expiry boundaries. Match consumptions against the actual prepared/bare/Yeti/retained variants offered by `Search`.

Result: **zero unsupported transitions; 123 action applications, 65 ordinary consumptions, 11 resource actions; 652 paid encounters; finished and targets true.** Fixed milk and terminal finishing are included in the count, so it is a conservative bound against 160 search layers. Original schedule ordered replay also passes. Final objective differs only by approximately `9.31e-10` Meat from different floating-point grouping of farming blocks; this is not a cleanup equivalence benchmark. The trace explicitly checks that cooling reservation release is a no-op in this fixture.

This demonstrates a currently legal core path **when pruning is bypassed**. It does not demonstrate that `Offer` admits each prefix, that a historical build retained the path, or that all practical plans are beam-expressible. It supports prioritizing completion-aware local ideas over widening or reviving the general beam. No new full-day search was implemented or run.

### B2. Joint buff pairs: zero-counter diagnosis

The [pair generator](../scripts/TeresMimicDiet.ash#L2264) increments `barfDietMenuPairsGenerated` only after two distinct retained effects satisfy eligibility, duration and organ-fit screens, but **before** the profitability estimate/top-12 selection. It does not increment for completed schedules.

The [caller near the end of QuickPlan](../scripts/TeresMimicDiet.ash#L2689) comes after fallback, early-XP trials, six starting seeds, multi-pour trials, wider fill, two menu/helper passes and training comparisons. The generator checks `QuickExpired` at each outer candidate, so an already-expired deadline returns immediately with zero generated pairs. Its later complete-trial loop also checks the deadline.

An isolated native probe against the same reconstructed initial state produced:

| Condition | Eligible pairs generated | Returned estimated-positive top pairs |
| --- | ---: | ---: |
| Deadline already expired | 0 | 0 |
| No deadline for this small generator call | 172 | 12 |

Thus budget starvation is a verified possible cause on this fixture. Other possible causes of zero are fewer than two eligible distinct effects or no pair fitting the reserved organ envelope. The historical screenshot has no complete source hash, preferences, deadline trace or candidate list attached to it, so its exact cause **needs verification**. Do not infer that zero means paired buffs have no value, and do not report 172 generated estimates as 172 complete comparisons.
